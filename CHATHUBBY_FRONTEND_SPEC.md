# CHATHUBBY FRONTEND SPECIFICATION

> Generated by reverse-engineering the backend codebase. This document contains everything a frontend agent needs to design and implement the ChatHubby frontend without inspecting the backend source code.

---

## Application Overview

**ChatHubby** is a real-time chat application supporting:

- User authentication (email/username + password) with Argon2id hashing
- Direct messages (DMs) between two users
- Group chat rooms with role-based membership (OWNER, ADMIN, MEMBER)
- Room join mechanisms: invitations, join requests, shareable links
- File/image/video/audio attachments via S3 presigned URLs
- Read receipts with unread counts
- Message editing (5-minute window) and soft deletion (30-minute window)
- Recovery code-based password reset

**Tech stack:**

- Backend: Express.js + Socket.IO + Prisma + PostgreSQL + Redis
- Server port: 3100
- Auth: Session-based (`express-session` with Redis store)
- Validation: Zod v4 schemas (shared `@repo/validators` package)

## Authentication

### Session Architecture

- **Mechanism:** Server-side sessions stored in Redis, identified by a cookie
- **Cookie name:** `chathubby.sid`
- **Cookie properties:**
  - `httpOnly: true`
  - `secure: true` in production, `false` in development
  - `sameSite: "lax"`
  - `maxAge: 604800000` (7 days)
- **Session data:** `userId` (string, user's primary key)
- **Session fixation protection:** Session is regenerated on login and signup
- **CSRF protection:** `tiny-csrf` (AES-256-CBC) applied to POST/PUT/PATCH/DELETE. Client must fetch CSRF token first via `GET /api/csrf-token` and send it in the `x-csrf-token` header on state-changing requests.

### Authentication Flow

```
1. GET /api/csrf-token → receive { csrfToken }
2. POST /api/auth/signup or /api/auth/login
   → Set-Cookie: chathubby.sid=...
   → Response: { ok: true, user: {...} }
3. All subsequent requests include credentials: "include" (fetch) or withCredentials: true (axios)
4. CSRF token sent in x-csrf-token header on POST/PUT/PATCH/DELETE
5. GET /api/auth/me → { ok: true, user: {...} } (check session validity)
6. POST /api/auth/logout → clears cookie, destroys session
```

### Password Reset

Uses **recovery codes** (not email-based):

1. User receives 10 recovery codes at signup (format: `RC_XXXXXX.XXXX-XXXX-XXXX`)
2. Codes are shown once and never retrievable again
3. Reset: `POST /api/auth/forgot-password` with `{ username, recoveryCode, newPassword }`
4. On success, new recovery codes are returned

## Authorization & Permissions

### User Roles (Chat Rooms)

| Role   | Description                                                |
| ------ | ---------------------------------------------------------- |
| OWNER  | Created the room. Full control.                            |
| ADMIN  | Can manage members, invitations, join links, join requests |
| MEMBER | Default role for joined users                              |

### Permission Matrix

| Action                        | Unauth | MEMBER | ADMIN | OWNER |
| ----------------------------- | :----: | :----: | :---: | :---: |
| View room list                |   No   |  Yes   |  Yes  |  Yes  |
| Send room message             |   No   |  Yes   |  Yes  |  Yes  |
| Edit own room message (5m)    |   No   |  Yes   |  Yes  |  Yes  |
| Delete own room message (30m) |   No   |  Yes   |  Yes  |  Yes  |
| Invite user to room           |   No   |   No   |  Yes  |  Yes  |
| Manage join requests          |   No   |   No   |  Yes  |  Yes  |
| Create/deactivate join links  |   No   |   No   |  Yes  |  Yes  |
| Send DM                       |   No   |  Yes   |  Yes  |  Yes  |
| Edit own DM message (5m)      |   No   |  Yes   |  Yes  |  Yes  |
| Delete own DM message (30m)   |   No   |  Yes   |  Yes  |  Yes  |
| Search users                  |   No   |  Yes   |  Yes  |  Yes  |

### DM Access

- Any authenticated user can start a DM with any other user (except themselves)
- DM participants: exactly two users (user1Id, user2Id stored with user1Id < user2Id)

### Attachment Access

- **PENDING attachments:** Only uploader can access
- **Room attachments:** Any room member can access
- **DM attachments:** Both DM participants can access
- **Delete attachments:** Uploader, message sender, or room ADMIN/OWNER

Rate-limited endpoints return these headers:

- `RateLimit-Limit`: Max attempts in the window
- `RateLimit-Remaining`: Remaining attempts

#### 2. POST `/api/auth/signup`

Creates a new user account and establishes a session.

**Auth:** No (but if already logged in, returns `{ ok: true, message: "Already logged in", userId }`)
**Rate Limit:** 5 requests per 15 minutes per IP:email
**Request Body:**

```json
{
  "email": "user@example.com", // required, valid email, trimmed
  "username": "johndoe", // required, 3-20 chars, alphanumeric + underscore
  "displayname": "John Doe", // required, 3-20 chars
  "password": "securepass123" // required, 8-72 chars
}
```

**Response 201:**

```json
{
  "ok": true,
  "user": {
    "id": "uuid",
    "email": "user@example.com",
    "displayname": "John Doe",
    "username": "johndoe",
    "createdAt": "2026-01-01T00:00:00.000Z"
  },
  "recoveryCodes": ["RC_XXXXXX.XXXX-XXXX-XXXX", "..."]
}
```

**Error Responses:**

- `400` — Validation error: `{ ok: false, error: "field: message" }`
- `409` — Duplicate: `{ ok: false, error: "Email already exists" }` or `{ ok: false, error: "Username already exists" }`
- `429` — Rate limited

**Side effects:** Session is created, recovery codes are generated.

---

#### 3. POST `/api/auth/login`

Authenticates a user by email or username + password.

**Auth:** No (but if already logged in, returns `{ ok: true, message: "Already logged in", userId }`)
**Rate Limit:** 5 requests per 15 minutes per IP:identifier
**Request Body (union — provide one):**

```json
// Option A: email
{ "email": "user@example.com", "password": "securepass123" }

// Option B: username
{ "username": "johndoe", "password": "securepass123" }
```

**Response 200:**

```json
{
  "ok": true,
  "user": {
    "id": "uuid",
    "email": "user@example.com",
    "username": "johndoe",
    "displayname": "John Doe"

}
```

**Error Responses:**

- `400` — Invalid input: `{ ok: false, error: "Invalid input" }`
- `401` — Invalid credentials: `{ ok: false, error: "Invalid credentials" }`
- `429` — Rate limited

**Note:** Login does not return `avatar` or `createdAt`. Use `GET /api/auth/me` for full profile.

**Auth:** Yes

**Response 200:**

```json
{
  "ok": true,
  "messages": [
    {
      "id": "uuid",
      "content": "Hello!" | null,
      "createdAt": "2026-01-01T00:00:00.000Z",
      "messageType": "TEXT",
      "isDeleted": false,
      "editedAt": null | "2026-01-01T00:05:00.000Z",
      "User": {
        "id": "uuid",
        "username": "johndoe",
        "displayname": "John Doe",
        "avatar": "https://..." | null
      },
      "attachments": [
        {
          "id": "uuid",
          "filename": "photo.jpg",
          "mimeType": "image/jpeg",
          "size": 1024000,
          "width": 1920,
          "height": 1080,
          "thumbnailKey": "attachments/thumbnails/..."
        }
      ]
    }
  ]

```

**Pagination:**

- **Initial load (no cursor):** Returns oldest N messages (ascending by `createdAt`)

## WebSocket / Socket.IO API

### Connection

- **URL:** `http://localhost:3100`
- **Transport:** WebSocket (with HTTP long-polling fallback)
- **Authentication:** Session cookie (`chathubby.sid`) sent automatically with `credentials: "include"`
- **Middleware chain:** Session parsing → Socket auth (reads `session.userId`, loads user from DB)

### Auto-Joined Rooms

On connection, the client automatically joins `user:{userId}`. This room is used for:

- `directChat:read` — DM read receipt updates
- `chatroom:read` — Room read receipt updates

### Manual Room Joining

For real-time messaging, the client must explicitly join:

- **Room chat:** Emit `chatroom:join` → joins Socket.IO room `room:{chatRoomId}`
- **Direct chat:** Emit `directChat:join` → joins Socket.IO room `directChat:{directChatId}`

### Socket Event Catalog

#### Client → Server Events

| Event                     | Payload                                                                                        | Purpose                            | Ack? |
| ------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------- | :--: |
| `chatroom:join`           | `{ chatRoomId: string }`                                                                       | Join a room for real-time messages |  No  |
| `chatroom:leave`          | `{ chatRoomId: string }`                                                                       | Leave a room                       |  No  |
| `chatroom:message`        | `{ payload: { chatRoomId, content, messageType, attachmentIds?, idempotencyKey? }, callback }` | Send a room message                | Yes  |
| `chatroom:message:edit`   | `{ payload: { chatRoomId, messageId, content }, callback }`                                    | Edit a room message                | Yes  |
| `chatroom:message:delete` | `{ payload: { chatRoomId, messageId }, callback }`                                             | Delete a room message              | Yes  |
| `directChat:join`         | `{ directChatId: string }`                                                                     | Join a DM for real-time messages   |  No  |
| `directChat:leave`        | `{ directChatId: string }`                                                                     | Leave a DM                         |  No  |

#### Server → Client Events

| Event                      | Payload                                          | When                                      |
| -------------------------- | ------------------------------------------------ | ----------------------------------------- |
| `chatroom:joined`          | `{ chatRoomId }`                                 | Successfully joined a room                |
| `chatroom:left`            | `{ chatRoomId }`                                 | Successfully left a room                  |
| `chatroom:error`           | `{ code, message }`                              | Error in room socket operations           |
| `chatroom:message`         | Message object with attachments                  | New message in a joined room              |
| `chatroom:message:edited`  | `{ messageId, chatRoomId, content, editedAt }`   | Message edited in a joined room           |
| `chatroom:message:deleted` | `{ messageId, chatRoomId, deletedAt }`           | Message deleted in a joined room          |
| `directChat:joined`        | `{ directChatId }`                               | Successfully joined a DM                  |
| `directChat:left`          | `{ directChatId }`                               | Successfully left a DM                    |
| `directChat:error`         | `{ code, message }`                              | Error in DM socket operations             |
| `message:new`              | Message object with attachments                  | New DM message                            |
| `message:edited`           | `{ messageId, directChatId, content, editedAt }` | DM message edited                         |
| `message:deleted`          | `{ messageId, directChatId, deletedAt }`         | DM message deleted                        |
| `inbox:update`             | `{ directChatId }`                               | Inbox should be refreshed                 |
| `directChat:read`          | `{ directChatId, unreadCount }`                  | DM read receipt update (to `user:{id}`)   |
| `chatroom:read`            | `{ chatRoomId, unreadCount }`                    | Room read receipt update (to `user:{id}`) |

### Ack Callback Pattern

Room message events (`chatroom:message`, `chatroom:message:edit`, `chatroom:message:delete`) use an acknowledgement callback:

```typescript
// Emit
socket.emit("chatroom:message", {
  payload: { chatRoomId, content, messageType, attachmentIds },
  callback: (response) => {
    // response: { ok: true, message: {...} } | { ok: false, error: string, code?: string }
  },
});
```

**IMPORTANT:** Events use a `{ payload, callback }` wrapper shape, NOT a flat payload. The actual data goes in `payload`, and the callback is the ack function.

### Room Membership Caching

Server caches room membership on the socket for 60 seconds. After joining a room, messages are authorized via cache until TTL expires. If a user is removed from a room, they can continue sending for up to 60 seconds until the cache expires.

## File Upload System

### Supported MIME Types

**Images:** `image/jpeg`, `image/png`, `image/gif`, `image/webp`, `image/svg+xml`
**Video:** `video/mp4`, `video/webm`, `video/ogg`
**Audio:** `audio/mpeg`, `audio/mp4`, `audio/webm`, `audio/ogg`, `audio/wav`, `audio/flac`
**Documents:** `application/pdf`, `application/zip`, `application/json`, `text/plain`, `text/markdown`, `application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `application/vnd.ms-excel`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`

### Upload Flow

```
1. Frontend: select file, determine context (room/dm/voice) and contextId
2. Frontend: POST /api/attachments/presign
   → { attachmentId, presignedUrl, s3Key }
3. Frontend: PUT file directly to presignedUrl (with Content-Type header)
4. Frontend: send message with attachmentIds: [attachmentId]
5. Server: verifies attachment (exists in S3, correct status, correct owner)
6. Server: transitions PENDING → ATTACHED, links to message
```

### Limits

- **Max file size:** 100 MB
- **Max attachments per message:** 10
- **Presigned URL expiry:** 5 minutes (both PUT and GET)

### S3 Key Structure

```
attachments/{context}/{contextId}/{uuid}.{extension}
```

Where `context` is `room`, `dm`, or `voice`, and extension is derived from MIME type.

### Thumbnail System

Not implemented — `thumbnailKey` field exists in the schema but is always `null` in current implementation.

## Pagination Specification

### Cursor-Based Pagination

All paginated endpoints use cursor-based pagination:

**Pattern:** Fetch `limit + 1` items, check if there are more, return `limit` items with `nextCursor`.

**Request:**

```
GET /api/dm/inbox?cursor=<last_item_id>&limit=20
```

**Response:**

```json
{
  "ok": true,
  "items": [...],
  "nextCursor": "uuid" | null
}
```

- `nextCursor: null` — No more items
- `nextCursor: "uuid"` — Pass as `cursor` param to get next page

### Paginated Endpoints

| Endpoint                       | Default Limit | Max Limit | Cursor Field   |
| ------------------------------ | :-----------: | :-------: | -------------- |
| `GET /api/dm/inbox`            |      50       |    50     | `directChatId` |
| `GET /api/dm/:id/messages`     |      50       |    100    | `message.id`   |
| `GET /api/room/rooms`          |      20       |    50     | `roomId`       |
| `GET /api/search/users/search` |      10       |    50     | `user.id`      |

### Message Pagination Direction

- **Initial load (no cursor):** Returns oldest N messages (ascending by `createdAt`)
- **Load older (cursor + direction=before):** Returns N messages before cursor (ascending)

The frontend should maintain a scrollable message list:

1. Load initial messages (ascending)
2. When scrolling up, request older messages with `direction=before` and cursor=oldest_visible_message_id
3. Prepend older messages to the list

### Frontend Error Handling Strategy

1. **401 Unauthorized:** Redirect to login page, clear local auth state

6. **500+ Server Error:** Show generic error, allow retry

## Core User Flows

### Flow 1: Registration

```
User clicks "Sign Up"
  → Fill form (email, username, display name, password)
  → POST /api/auth/signup
  → Server creates user, generates recovery codes, creates session
  → Frontend shows recovery codes (MUST display — they are never retrievable again)
  → Frontend stores session cookie
  → Redirect to dashboard
```

### Flow 2: Login

```
User clicks "Log In"
  → Fill form (email or username + password)
  → POST /api/auth/login
  → Server verifies credentials, regenerates session
  → Frontend stores session cookie
  → Redirect to dashboard
```

### Flow 3: Starting a DM

```
User searches for another user
  → GET /api/search/users/search?query=john
  → Results list with usernames
  → User clicks a result
  → GET /api/search/users/:id (get full profile)
  → User clicks "Send Message"
  → POST /api/dm/start-dm/:userId
  → Server creates or returns existing chat
  → Frontend navigates to DM chat view
  → Socket: emit directChat:join
  → Load messages: GET /api/dm/:directChatId/messages
```

### Flow 4: Sending a Message (DM)

```
User types message
  → Frontend sends message via POST /api/dm/:directChatId/message
  → Server validates, persists, emits to directChat:{id} room
  → All participants receive message:new event
  → Frontend appends message to conversation
```

### Flow 5: Sending a Message (Room)

```
User types message
  → Socket: emit chatroom:message with { payload, callback }
  → Server validates, persists, broadcasts to room:{id}
  → All room members receive chatroom:message event
  → Frontend appends message to conversation
  → Callback receives { ok: true, message } or error
```

### Flow 6: Sending Attachments

```
User selects file(s)
  → Frontend: POST /api/attachments/presign (for each file)
  → Receive presignedUrl + attachmentId
  → PUT each file to presignedUrl
  → User sends message with attachmentIds: [attachmentId1, attachmentId2]
  → Server verifies, links to message
  → Messages with attachments broadcast normally
```

### Flow 7: Receiving Messages in Real Time

```
Frontend connects socket
  → Auto-joins user:{userId} room
  → When viewing DM: emit directChat:join → joins directChat:{id} room
  → When viewing room: emit chatroom:join → joins room:{id} room
  → Listen for:
    - message:new → prepend to conversation
    - message:edited → update message content in place
    - message:deleted → show deletion marker / remove
    - inbox:update → refresh inbox list
    - directChat:read → update unread count badge
    - chatroom:read → update unread count badge
```

### Flow 8: Marking as Read

```
User opens a conversation
  → Frontend scrolls to bottom / marks last message as read
  → POST /api/dm/:directChatId/mark-read { lastReadMessageId }
  → Or POST /api/room/:chatRoomId/mark-read { lastReadMessageId }
  → Server updates read receipt, returns unreadCount
  → Server emits directChat:read or chatroom:read to user:{userId}
  → Other tabs/devices update unread badge
```

### Flow 9: Editing a Message

```
User hovers over own message → clicks Edit
  → (DM) PATCH /api/dm/message/:messageId { content: "new text" }
  → (Room) Socket: emit chatroom:message:edit { payload: { chatRoomId, messageId, content } }
  → Server validates: is owner? within 5-minute window?
  → On success: message:edited event broadcast
  → Frontend updates message content, shows edited indicator
```

### Flow 10: Deleting a Message

```
User hovers over own message → clicks Delete
  → (DM) DELETE /api/dm/message/:messageId
  → (Room) Socket: emit chatroom:message:delete { payload: { chatRoomId, messageId } }
  → Server validates: is owner? within 30-minute window?
  → On success: message:deleted event broadcast
  → Frontend shows deletion marker (soft delete — message content nulled, isDeleted=true)
```

### Flow 11: Creating a Room

```
User clicks "Create Room"
  → Fill form (name, description)
  → POST /api/room/rooms { name, description }
  → Server creates room with creator as OWNER
  → Frontend navigates to room
  → Socket: emit chatroom:join
```

### Flow 12: Joining a Room via Link

```
User receives link: /join/{token}
  → GET /api/room/join/:token (preview room info)
  → User confirms join
  → POST /api/room/join/:token
  → Server validates link, adds user as MEMBER
  → Frontend navigates to room
```

### Flow 13: Joining via Invitation

```
User receives invitation
  → GET /api/room/invitation/received (shows pending invitations)
  → User clicks Accept
  → PATCH /api/room/invitations/:invitationId { status: "ACCEPTED" }
  → Server adds user as MEMBER
  → Frontend refreshes room list
```

### Flow 14: Password Reset

```
User clicks "Forgot Password"
  → Fill form (username, recovery code, new password)
  → POST /api/auth/forgot-password
  → Server redeems code, returns new recovery codes
  → Frontend shows new codes (MUST display — shown once)
  → Redirect to login
```

## Frontend Integration Hazards

### 1. Socket Event Payload Wrapper

Room message events use `{ payload, callback }` wrapper. The actual data goes in `payload`, NOT as a flat event argument. Forgetting this wrapper will silently fail.

### 2. Room Messages HTTP Endpoint Does Not Exist

`GET /api/room/:chatRoomId/messages` does NOT exist in the backend. Room messages are only available via socket events after joining. The frontend must handle this — room messages can only be loaded via real-time socket events, not via REST. **This is a known gap documented in `todo.md`.**

### 3. CSRF Token Required

All POST/PUT/PATCH/DELETE requests need the CSRF token in `x-csrf-token` header. Must fetch from `GET /api/csrf-token` first. Forgetting this causes 403 errors on all mutations.

### 4. Session Cookie SameSite

Cookie is `sameSite: "lax"`, meaning it's sent on top-level navigations but NOT on cross-origin POST requests. Frontend must use `credentials: "include"` for fetch or `withCredentials: true` for axios.

### 5. DM User Ordering

`DirectChat` stores users with `user1Id < user2Id` (UUID string comparison). When displaying "the other user", check which side the current user is on: `chat.user1Id === myId ? chat.user2Id : chat.user1Id`.

### 6. Room Messages Not Persisted as List

Room messages arrive only via socket after joining. If the client refreshes, it loses message history until it rejoins the room via socket. There is no REST endpoint to fetch room message history.

### 7. Edit/Delete Windows are Server-Side

The 5-minute edit and 30-minute delete windows are enforced server-side based on `message.createdAt`. The frontend should check this client-side too (disable edit/delete options after the window), but the server is the source of truth.

### 8. Message IDs are CUIDs, Not UUIDs

Room message schema validates `chatRoomId` as `z.string().min(1)` (not UUID). DM message params use `z.string().min(1)`. User-related params use UUID validation. Don't assume all IDs are UUIDs.

### 9. Soft-Deleted Messages

Deleted messages have `isDeleted: true` and `content: null`. They still appear in the message list. The frontend should display a "Message deleted" placeholder, not remove them from the UI.

### 10. Recovery Codes Displayed Once

Recovery codes are returned in the response only at signup and password reset. They are never retrievable again. The frontend MUST display them clearly and warn the user to save them.

### 11. Login Response is Minimal

Login returns `{ id, email, username, displayname }` — no `avatar` or `createdAt`. Call `GET /api/auth/me` for the full profile after login if those fields are needed.

### 12. DM Messages Initial Load is Ascending

Initial load (no cursor) returns oldest messages first (ascending by `createdAt`). The frontend should render them and scroll to the bottom. For "load more", use `direction=before` with cursor.

### 13. Typing Indicators Not Implemented

There are no typing indicator socket events. The frontend should not attempt to implement them unless the backend adds support.

### 14. User Presence/Online Status Not Implemented

There is no online/offline status tracking. The frontend should not show presence indicators unless the backend adds support.

### 15. No Room Messages REST Endpoint

The `todo.md` explicitly notes: "Frontend `RoomMessages` calls `GET /room/:chatRoomId/messages` but no server handler exists." This is a known gap. Room message history can only be received via real-time socket events after joining.

## Known Backend Limitations

1. **No room messages HTTP endpoint** — Room messages can only be received via real-time socket after joining. No REST endpoint to fetch history.
2. **No typing indicators** — No socket events for typing state.
3. **No online/presence tracking** — No way to know if a user is online.
4. **No message reactions** — Not implemented (noted in todo.md).
5. **No message search** — Not implemented (noted in todo.md).
6. **No file deletion cleanup** — Orphaned S3 objects may exist if DB deletion fails.
7. **No profile update endpoint** — `userZod.updateMe` schema exists but no route handler implements it.
8. **No avatar upload endpoint** — Avatar field exists on User but no upload flow is implemented.
9. **No room member list endpoint** — No endpoint to list room members (only count via `_count`).
10. **No unread count on individual messages** — Unread state is only tracked per-conversation via read receipts, not per-message.
11. **Socket room membership cache** — 60-second TTL means removed members can continue sending for up to 60 seconds.
12. **No rate limiting on room socket messages** — Rate limiters are on HTTP endpoints but not on socket `chatroom:message` events.
